# Proportionate verification contract

Task: verification-proportionality. Parent: /root. Risk: high (core guard/review policy change). Executor: explicit Luna/high; no delegation. User authorized the proposed risk-based reduction.
Objective: remove unnecessary review calls, duplicated records and repeated suites while retaining actual safety gates. Current 77-test accepted tree and before.json are the baseline; do not rerun that unchanged baseline.

## Required behavior
- Parent selects low, standard or high risk with a short reason before dispatch; worker cannot downgrade it. Ambiguity about security/data/external effects returns to parent before dependent work.
- Low: documentation/prose, trivial reversible changes without changed security, API/data contracts or operational behavior. Run only applicable quick checks; parent checks result and accepts. No separate reviewer by default.
- Standard: ordinary feature/bug changes with bounded impact. Run changed-area tests; parent checks and accepts. Independent Sol/medium review is optional, selected for uncertainty, cross-module impact or explicit request. Unused optional review is N/A with one reason, not a failure.
- High: authentication/authorization, sensitive data handling, DB schema/migrations, destructive operations, deployment/recovery, external activation, or core harness routing/access/model/verification guards. Relevant integration checks plus independent Astra/high review required before parent acceptance; failed or absent required evidence cannot pass. File extension/size alone never determines low risk (policy documentation can be high).
- Root Astra remains orchestrator. Saved reviewer default Astra/high remains for high-risk review; explicit generic Sol/medium invocation with the same read-only reviewer role is valid for optional standard review and normal mandatory plan review. Do not add another agent. Record actual selected model/effort once; native stale pinned model may use explicit generic role.
- Keep UI specialist planning and independent ui-plan-review before UI behavior implementation. Reuse matching approved plans when unchanged; normal UI plan review may use Sol/medium, high-risk plans require Astra/high. Keep product planning specialist and existing plan-review gates, with Sol/medium for normal plans. These targeted planning gates do not imply separate Astra implementation review for every task.
- Keep independent release readiness/outcome, exact SHA/CI, authorization, external prerequisite immediate stop, no self-approval, and Luna -> Terra -> Sol executor ladder/three total attempts. Worker reports evidence only; parent acceptance of low/standard work is not worker self-approval or fabricated independent pass.
- Use one compact TASK-RECORD.md for assignment, acknowledgement/result and parent disposition. Minimum: task/scope+acceptance; risk/reason+applicable gate; selected role/model/effort; relevant checks with actual result/evidence; blockers; parent disposition. Keep context/outputs bounded via terse links. No mandatory separate ASSIGNMENT/IMPLEMENTATION-CONTRACT/RESULT/MODEL-USAGE files for low/standard work if this record contains required information. Inline task message/response may carry the compact record for trivial work; no durable file/journal entry for every small edit. Retain detailed templates for high-risk/complex work and existing references as available formats.
- MODEL-ESCALATION is required only for real capability-based model escalation, not routine handoff, same-model correction, same-cost alternative or ordinary reassignment. Allow a linked section in the single record; do not duplicate evidence into templates.
- During iteration run targeted relevant tests. Run the full applicable suite once at the completed change-batch boundary when executable harness/validator/guard behavior changed; prose-only edits do not trigger full regressions or UX smoke. UX smoke only when UX guidance/search/runtime changes. Standalone Factory only when common schema/provider projection changes; project structural checker already embeds factory validation. Provider preflight only when projecting adapters, not every correction. Git tracked verification only when tracking/delivery is requested, not every local change.
- Reviewer reads existing actual logs/results; do not rerun to reproduce passing output. Rerun only changed/invalidated tests, failures or genuinely inadequate evidence, recording the reason. Corrections re-review affected criteria only. Raw outputs in evidence file, concise summaries with links; do not reconstruct logs.

## Implementation and scope
- Prefer one small structured verification policy JSON as enforcement source, with a concise policy reference; guard required risk tiers, high-risk reviewer, optional standard review and run triggers without building a scheduler/NLP engine. Avoid more natural-language blacklist tests or exact prose locks; validate stable machine policy values and representative behavior/mutation cases.
- Allowed: harness/harness-spec.json only descriptive evaluator/applicability/reference changes needed for conditional review (preserve six roles/access/eight-edge DAG/specialist+release gates); all relevant harness roles, skills, templates, workflows, loops, recovery, rubric, HARNESS/ENVIRONMENT/team/ledger-format/model policy; matching .agents skill projections and .codex role instruction wrappers as needed, preserving saved models/access/limits. Add policies/VERIFICATION.json (or equivalent concise named structured file), templates/TASK-RECORD.md. Modify scripts/verify-harness.py and scripts/test_verify_harness.py. Update only AGENTS.md managed block, docs/architecture/orchestration-model-policy.md and docs/architecture/ui-ux-agent-guide.md as concise Korean reader guidance.
- No app/backend/frontend/infra/deploy/CI/vendor changes; no README/history rewrite, new roles/skills/evaluators, normal Git index/commit/push or external operations. Parent owns state/journal/decisions/baseline/contract/archive. You are not alone; preserve all earlier uncommitted changes.
- Remove or scope conflicting unconditional independent-Astra/full-suite/all-evidence-field requirements throughout active files and verifier/tests. Older maintenance evidence/reports are history, not active instruction. Do not weaken access, external-stop, high-risk review, UI and release prerequisites or provider parity to make tests pass.

## Acceptance and evidence
1. Low record can be accepted by parent with relevant checks and no reviewer; standard optional review uses Sol/medium; missing high-risk Astra review is rejected by applicable policy/rubric.
2. Risk trigger guards cannot be disabled/downgraded by cheap defaults; worker cannot self-approve. UI/release prerequisite tests still pass.
3. Single record and actual escalation-only evidence supported consistently; old unconditional clauses are scoped or removed in source AND projections.
4. Iterative targeted checks and one batch-end full suite, conditional UX/provider checks and evidence reuse are documented consistently.
5. Focused new policy regressions plus full suite once at final boundary; project verifier and diff check. Run preflight before projection; run standalone Factory once if required by provider changes. Skip UX smoke if UX vendor/search guidance unchanged with reason.
6. Return <=250 words, changed paths and actual command arrays/cwd/exit/stdout/stderr in result.md/checks.json here. Capture directly with subprocess, UTF-8 encoding, no placeholder commands or summarized output labeled raw. Freeze for one independent Astra review. No repeated parent suite if evidence is valid.
