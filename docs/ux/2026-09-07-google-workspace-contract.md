## Product decisions and exclusions

1. Project selection remains first depth. Account menu exposes personal Google connection, Drive browsing, and Gmail. Project files are explicit shared reference metadata, not a personal inbox. Calendar binding is project configuration controlled by a MANAGER.
2. Drive attachment means a project reference: provider file ID, display name, MIME type, safe canonical Google link, attaching actor/time. No binary download/replication, Google sharing/permission modification, schedule attachment, or automatic project visibility of unselected files. MANAGER/MEMBER can attach; VIEWER reads existing references; creator or current MANAGER removes a reference only. Check provider metadata in the caller's Google account immediately before attach. Deduplicate project+file ID.
3. Gmail is personal. Read inbox/sent/search and plain-text message detail; compose new mail with To/Cc/Bcc, subject, body; explicit review then send. No SMTP, automatic recipient inference, project mailbox, background send, Gmail draft synchronization, deletion, forwarding, reply threads, or binary mail attachments. Gmail viewing never marks read implicitly. Links to Gmail may supplement actual in-app read/send.
4. Calendar: one explicitly selected existing writable Google calendar per project, authenticated binding owner must be a current project MANAGER. Export CONFIRMED and previously-confirmed CANCELLED schedules with businessRevision>0; never export DRAFT or canceled drafts. Use stable deterministic event IDs, no Google attendees or notification emails (sendUpdates=none), no external edit import. Binding is immutable while present; disconnect before choosing another target. Disconnect stops new dispatch and leaves exported Google events intact; already-issued HTTP can still finish and the UI states this. Rebinding reconciles by deterministic IDs. ERP remains authoritative.
5. Implementing mail sending is authorized. Tests must use synthetic HTTP providers only; agents must not send real messages, edit real calendars, alter real Drive ACLs, or mutate production configuration. Public push/PR/deploy remain outside current authorization.

## OAuth, credentials, and module contracts

- Keep existing google client registration and /login/oauth2/code/google callback. Login requests openid/email/profile only. Authenticated POST /api/v1/google/connect with {feature: DRIVE|GMAIL|CALENDAR} creates a single-use 10-minute session-bound connect intent and returns {authorizationUrl} pointing to the local /oauth2/authorization/google flow. Do not accept arbitrary return URLs/scopes; connect outcomes return fixed /#/account/google with an allowlisted outcome code. Resolver adds only requested feature scopes, access_type=offline, include_granted_scopes=true and explicit consent for connection/reconnection; bind intent to OAuth state, ERP user, original Google subject, and current app session.
- Capture original ApplicationPrincipal before Spring replaces authentication during callback. Successful connection requires the same Google subject, verified email, valid unconsumed intent/state/session, and all required feature scopes. Then store grant against ERP userId+Google subject and restore the original app authentication. Different account, canceled/failed/expired/replayed intent, or insufficient scopes must preserve the original login/profile and prior vault, return a safe connection outcome, and never run ordinary login provisioning or invalidate the app session. OAuth login failure behavior remains separately defined. Cover Spring authorized-client sub key versus ERP UUID explicitly; consume/remove framework temporary authorized clients after secure capture, without persisting plaintext credentials in browser/session.
- Scopes: Drive drive.metadata.readonly; Gmail gmail.readonly and gmail.send; Calendar calendar.calendarlist.readonly and calendar.events. Accept provider-documented broader equivalents already granted (Drive drive/drive.readonly, Gmail gmail.modify/mail.google.com, Calendar calendar) only by explicit capability mapping. Do not fabricate granted scopes from requested/Console scopes. Missing refresh token with no existing one means reconnect required; preserve existing refresh token on a valid same-subject grant when omitted. Do not regress already granted features during incremental consent.
- Vault resides in identity, encrypted AES-256-GCM with random nonce and authenticated userId/subject context; key is server-only GOOGLE_TOKEN_ENCRYPTION_KEY (base64 32 bytes). APP_GOOGLE_WORKSPACE_ENABLED defaults false. Enabled integration needs configured OIDC and a valid key; absent configuration is an explicit safe state, not a dummy connected result. Document restart/key backup requirements without printing/generating real keys in tracked files. V8 adds identity.google_authorization keyed by user, ciphertexts, scope set, expiresAt, subject binding and generation/version. No raw token, authorization code, provider error body, or token-bearing URI in API responses, logs, displayName, traces, or frontend storage.
- Refresh per-user grant under bounded concurrency with generation compare-and-set; refresh-token rotation and disconnect must not be overwritten by stale refresh/callback. invalid_grant marks only that grant REAUTH_REQUIRED; 403 missing scope is permission missing, not global logout. Fixed Google HTTPS hosts, bounded response sizes and 10s request deadlines, no redirect following or automatic POST retry. HTTP clients are injectable for localhost test doubles without production endpoint environment overrides. Exceptions expose only allowlisted safe codes.
- Identity exports a named Java API GoogleAccess: status(UUID), credential(UUID, Feature) -> server-only Credential(accessToken,generation), isCurrent(UUID,generation), plus safe error categories. Credential toString must redact. Google workspace and Calendar consume this API; identity must not depend on either consumer. Existing identity::api/ApplicationPrincipal is authoritative. Controllers always derive account from authenticated principal, never body/query user IDs.
- GET /api/v1/google/connection -> {configurationRequired, accountEmail, drive:{status},gmail:{status},calendar:{status}}, status one of CONNECTED,NOT_CONNECTED,PERMISSION_REQUIRED,REAUTH_REQUIRED; no tokens/scopes required in UI. DELETE /api/v1/google/connection clears local vault, increments generation and stops further exports, retaining app login; do not call Google revoke because the same grant also serves login. CSRF required for all mutations, Cache-Control:no-store for private responses. Reconnect/denial responses clear displayed private resource data across route/session transitions.

## Drive and Gmail HTTP contracts

- GET /api/v1/google/drive/files?query=&pageToken= -> {files:[{id,name,mimeType,url,modifiedTime}],nextPageToken}. Max20/page, orderBy modifiedTime desc, name search max200 with correctly escaped Drive query, trashed=false, bounded opaque page token. Provider fields only id/name/mimeType/modifiedTime, URL constructed from validated file ID under https://drive.google.com/open?id=... . No arbitrary external URL fetched. GET /api/v1/projects/{id}/files?page= -> {files:[{id,fileId,name,mimeType,url,attachedBy,attachedAt,canRemove}],hasNext}, max25; POST {fileId} -> reference; DELETE /files/{referenceId} ->204. Persist google_workspace.drive_reference; project existence/current role checked before provider calls and again before storing their result. Same-project ID binding and cross-user/project denial tests required.
- GET /api/v1/google/mail/messages?folder=INBOX|SENT&query=&pageToken= -> {messages:[{id,subject,from,to,snippet,internalDate,unread}],nextPageToken}; max20 rows and bounded detail fanout at20. Provider full response/header/body never returned raw. GET /api/v1/google/mail/messages/{id} -> {id,subject,from,to,cc,date,bodyText,truncated}. Parse bounded MIME parts/depth and base64url; prefer text/plain. HTML-only messages become inert text, no raw HTML rendering, remote image fetch, embedded scripts or provider URLs in DOM. Bound provider response to2MB and displayed body100k; mark truncation. Validation errors/metadata fields cannot echo credential strings.
- POST /api/v1/google/mail/send {requestId UUID,to:string[],cc:string[],bcc:string[],subject:string,body:string} -> {requestId,status:SENDING|SENT|UNKNOWN|FAILED,messageId?}. Validate at least one To, total1..20 recipients, each plain valid email with no CR/LF; subject1..200 no CR/LF, body<=100000. MIME From is server identity email; use trusted MIME library/RFC encoding for Unicode subject/body, no user-controlled extra headers. No credentials in stored MIME logs. Server sends once to users/me/messages/send; no external test send.
- Persist google_workspace.mail_send_request (V8 creates google_workspace schema), keyed user+requestId, normalized payload SHA256, status, created/updatedAt, messageId. Commit SENDING before provider HTTP, finish in separate transaction and account/generation guard. Same key+payload replays receipt, mismatch409, other user cannot query it. Unknown transport/5xx or crash after claim never triggers automatic resend; age-out SENDING older than60s to UNKNOWN. GET /api/v1/google/mail/sends/{requestId} reads/reconciles receipt only and never resends. Store no body/recipient content in receipt. UI holds attempt through remount and keeps only requestId/account namespace in sessionStorage for reload; new compose must not silently resend prior content. Explicit review precedes send; UNKNOWN offers status check and open Gmail sent folder, not a blind retry. Promise at-most-one automatic provider attempt per key, not externally guaranteed exactly-once delivery.

## Calendar interface and delivery

- GET /api/v1/google/calendars?pageToken= -> {calendars:[{id,name}],nextPageToken}; max50, writable owner/writer only. Project GET /api/v1/projects/{id}/calendar -> {status:NOT_BOUND|BOUND|REAUTH_REQUIRED,calendarName?,ownerName?,isOwner,canManage,backfillPending}; current member allowed. POST same path {calendarId} (MANAGER only) binds caller's Google account after provider permission validation; duplicate identical binding replays, different binding409. DELETE removes local binding only, preserves exported events, MANAGER only. Legacy /calendar/connection and /calendar/reconnect remain compatible, with reconnect status refresh only and correct UI wording.
- Core V8 adds project_calendar.binding_owner UUID FK identity.user_account(id), binding_generation BIGINT NOT NULL DEFAULT0, calendar_name VARCHAR(255), backfill_cursor UUID, backfill_pending BOOLEAN NOT NULL DEFAULTfalse; existing external_calendar_id/calendar_connection_id retained. Add calendar_projection.claim_token UUID, lease_until TIMESTAMPTZ, delivered_revision BIGINT NOT NULL DEFAULT0. Calendar worker uses these exact names; further schema changes require parent revision. On binding, set backfill_pending and process existing schedules in persisted UUID-cursor pages of100 via ScheduleLookup; continue until exhausted. On disconnect clear owner/target/name, increment binding_generation and invalidate old claims. Rebinding to a different target preserves old events and exports to the new target; UI explicitly describes that result.
- CalendarEventConsumer remains local durable projection/outbox only. Dedicated enabled worker claims bounded pending projections in a short transaction, performs HTTP outside DB/schedule transaction, and conditionally completes using claim token+schedule business revision+binding generation+credential generation. Newer revision/binding/unlink/demotion cannot be overwritten by stale completion. Retry dispatch follows same path; at most one active claim, expiring lease permits recovery with deterministic provider event IDs. Check current binding owner MANAGER before each external call; account disconnect or lost permission blocks exports.
- ScheduleLookup exports one bounded immutable snapshot by projectId+scheduleId (title,description,startsAt,endsAt,status,businessRevision) and bounded UUID-cursor export page, no direct schedule entity/repository access from other modules. Events use UTC dateTime, stable base32hex-compatible ID derived from project+schedule, private extended properties for project/schedule/revision. Insert conflict reconciles existing matching event before update; never overwrite unrelated provider event. Updates use provider ETag/If-Match and compare exported revision. Before every external operation recheck current local claim, desired revision, binding and credential generation. On changed desired state a late completion queues latest reconciliation, not SYNCED.
- Cancellation is durable in the LOCAL projection; Google cancelled records may lose metadata or disappear. For desired CANCELLED, GET404/410 means absent/success and must NEVER insert; cancel existing matching events conditionally. Do not rely on permanent Google tombstones/extended properties. Existing in-flight requests cannot be withdrawn; retain local cancellation and perform bounded periodic reconciliation of canceled projections where an older uncertain claim might have completed. Stale claims must not dispatch new inserts after a local cancel. Claim leases60s exceed HTTP deadline10s, but do not promise external exactly-once or zero transient visibility after an issued HTTP. Reauthorization/permanent/transient statuses remain meaningful; no Gmail automatic resend through Calendar workers.
