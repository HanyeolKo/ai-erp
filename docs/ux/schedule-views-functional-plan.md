## Workflow and screen structure

- Route parsing: split hash once into `pathname` and `queryString`; match every project route against `pathname`, parse query with `URLSearchParams`, and ignore/replace invalid or unauthorized `view`, `date`, `mode`, `page` values without exposing resource existence.
- Context: schedules URL carries `view=<builtin-or-authorized-id>`, Calendar `mode=month|week` and `date`, or Cards/List `page`; record links add a validated return context. Cancel/back and successful create/edit/detail return restore that context. A missing/archived/forbidden personal view falls back to matching builtin and announces why.
- View bar: first show immutable `builtin-calendar`, `builtin-cards`, `builtin-list` to every project reader without manager initialization, then active shared views and actor-owned personal views. Selection runs `POST W/query`; one clearly named “View settings” action opens configuration.
- Dirty configuration stays local until Save. Customizing a builtin offers “Save personal copy”; MANAGER may instead create shared. Owners save/rename/archive personal views; MANAGER saves/renames/archives shared views. Duplicate always POSTs a new named PERSONAL or, for MANAGER, SHARED view; scope never mutates and “make shared” is an explicit copy.
- The settings Dialog has ordered sections: name/scope, filter rows, group, legend, ordered sorts, visible fields. Field choice constrains operator/value controls to the API matrix; empty operators hide operand; archived references remain labelled “Archived” with Remove filter/field and manager Unarchive paths rather than silent rewrites.
- Saving validates name/caps/duplicate fields locally, then server truth. `409` preserves the draft, offers Reload latest and Duplicate draft; `400` places field errors beside the relevant row and focuses the first error. Save success selects the returned ID and clears dirty state.
- Calendar uses fixed `startsAt`/`endsAt`, current month/week navigation, drag/move/resize, preview, lock/recovery, and accessible time-change Dialog. Load all pages for the visible half-open range up to 1000; if capped/fails mid-load, label the view partial, keep loaded events operable, and offer narrower range/refresh. Drag is never the only edit path.
- Cards displays server-ordered record cards with title, configured fields, independent legend, group headings/counts (including unset/archived options), total and real pagination. Card Create opens the atomic schedule form; Edit opens the record form, while permitted property values may also edit inline with explicit Save/Cancel.
- List uses a semantic table on desktop: title first, then configured fields, row actions, total and real pagination. On narrow screens each row becomes a labelled record block in the same field/order sequence; no horizontal page overflow. Row/card/title all target the same schedule ID.
- Filter/group/legend/sort changes refresh from page 0; server `total`, `groups`, deterministic order, and `hasMore` are authoritative. While refetching, retain and mark prior content stale; deduplicate IDs; after any write invalidate Workspace, active query, dashboard selection, record detail, and legacy schedule/dashboard queries.
- MANAGER “Properties” opens a schema editor ordered by `position`, then ID, with active then archived status. Create chooses TEXT/NUMBER/CHECKBOX/DATE/SINGLE_SELECT once; rename/archive/reorder PATCH requires `rowVersion`. Reorder uses a labelled integer position input (0..10000), so it remains keyboard accessible.
- SINGLE_SELECT option rows have stable hidden IDs, label, allowed color token, archive/unarchive, and explicit Move up/Move down buttons; their submitted full-array order is canonical. Supplying options sends every current option, and all view/property/dashboard PATCH actions include the displayed expected version.
- Before property/option archive, explain stored-value and saved-view impact and show `valueCount` when supplied; archive preserves values/references and blocks new assignments. At caps (50 properties/100 options) creation is disabled with the exact limit. No hard delete, type conversion, or invented default value control appears.
- Record create/edit is one form submission to `POST/PATCH W/records`: existing fixed fields/participants plus a “Project properties” fieldset generated from active definitions. Inputs are text, finite number, checkbox, local date, or select; clear sends null, untouched edit keys may be omitted, and archived stored values appear read-only with Clear.
- Detail adds a “Project properties” section with all stored values, including labelled archived definitions/options. An authorized manager/creator uses Edit or inline value Save through `/values`; VIEWER and non-owner MEMBER see text only. Fixed-field edits keep existing business behavior; custom-only writes visibly state they do not change acknowledgements or Calendar.
- Atomic save failure leaves fixed and custom drafts intact. On `409`, show latest values beside changed draft fields and require Reload latest or intentional re-entry; never replay automatically. After success, if the record no longer matches the active saved filter/group, remove it only after confirmation text (“Saved; hidden by this view”) with Open detail and Clear filters actions.
- Dashboard retains onboarding, upcoming schedules, action queue, three counts, and their existing permissions/order. Add one schedule-view section: MANAGER chooses an active SHARED view or builtin, others read the selection; personal views never appear. An absent row is `dashboardViewId:null`/version 0 and renders builtin Cards; first PATCH sends 0 and returns 1, later writes send the latest version. Reset sends null.
- Dashboard queries the selected view config but renders compact, paged cards regardless of its peer presentation type. Cards are real record links and expose the same permitted inline custom-value edit or full Edit action; VIEWER/non-owner remains read-only. An archived/unavailable reference shows no stale records and gives MANAGER Reset, others an availability message.

## State and accessibility coverage

- Initial/loading/empty: Workspace skeleton-free status text; builtin tabs may render while metadata loads but query controls wait for validated config. Distinguish no project schedules, no filter matches, no groups, and no dashboard selection. Preserve prior safe results during refresh with `aria-busy` and a polite status.
- Partial/error/recovery: separate metadata, query-page, mutation, permission, stale-version, partial Calendar, and unavailable-dashboard messages. Retry uses captured session context; a fresh role/read check is required before clearing a denial. Never reveal another actor’s personal-view name/count.
- Disabled/success: disabled controls explain role, cancelled record, cap, pending write, or archived target. Success announces saved view/value/record and new location; destructive-looking archive uses a confirmation Dialog, while reversible view/property archive is named Archive, not Delete.
- Keyboard/focus: DOM order is view bar, view actions, configuration controls, results, pagination. Use buttons/tabs with accessible names and pressed/selected state; every filter row and option control has a persistent label. Dialog traps Escape/caller return; validation focuses first error; add/remove/reorder has button alternatives; Calendar time Dialog remains the keyboard/single-pointer alternative to drag/resize.
- Legend/group never rely on color: show option label, swatch, count, “Unset”, and “Archived”. Announce inline edit mode and save outcome. Preserve skip link/route h1 focus, 4.5:1 text and 3:1 control/focus target, reduced motion, and no clipped focus.
- Mobile `<768px`: view bar and filter chips wrap or use an operable disclosure; settings becomes one-column; actions wrap without reordering; Cards/List use labelled blocks; Calendar keeps the existing agenda alternative and period/time Dialog, with no drag requirement or global horizontal overflow.

## Decisions and acceptance criteria

- AC1: all authorized readers immediately receive three builtins with zero seed write; saved personal/shared CRUD, immutable scope/copy semantics, permissions, archived-reference recovery, required write versions, and route restoration match API r2.
- AC2: filters, group, custom legend, sorts, visible fields, counts, and pagination come from complete authorized server results; Cards/List never treat a 20/50/100-row client page as complete and Calendar visibly caps at 1000.
- AC3: five-type schema and option management preserves stable IDs/values/references across rename/reorder/archive; author/manager/VIEWER controls match existing schedule and new view/schema rights.
- AC4: Calendar retains month/week, direct manipulation and Dialog recovery; Cards, List, dashboard, form, and detail edit the same schedule ID, with atomic fixed/custom saves and explicit conflict/hidden-after-save behavior.
- AC5: dashboard keeps existing counts/queues/onboarding and renders editable selected-view cards; invalid selection cannot leak/stale-render and can be reset. Personal views cannot be selected.
- AC6: at 1440, 768, 390, 375, 320px/200% zoom, all actions, labels, values, status, focus, pagination, and recovery remain operable; keyboard-only users can complete every pointer workflow.
- Planned checks: role/ownership matrix, URL restoration/fallback, five type/null/archive/config caps, stale conflicts, >100 rows/count/group/sort/page, Calendar 1000 partial, dashboard unavailable, atomic rollback, cross-view invalidation, keyboard/Dialog/reflow/contrast, and existing lifecycle/ACK/projection regression.
- Checks not run: code diff, generated client, unit/integration/PostgreSQL/Flyway, typecheck/build, browser screenshots, keyboard, contrast, live Google, deployment, and Notion archive. Reviewer evidence target: `docs/ux/schedule-views-ui-review.md`; any API/plan revision invalidates this plan.
