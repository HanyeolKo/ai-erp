## Workflow and screen structure

- Keep the existing shell and compact left-aligned hierarchy: page heading, state explanation, primary next action, secondary refresh, and existing navigation. Add a plainly named `프로젝트 선택` link to shared navigation so recovery does not depend on recognizing the brand as a home link. Keep notifications and Calendar available after authentication because their existing APIs do not require a selected project.
- First-page empty state: retain heading `프로젝트` and text `참여 중인 프로젝트가 없습니다.` Ask `새 프로젝트를 만드시겠어요?` and load the independent creation-options query. Present the creation region first, then `초대 링크로 참여` with `프로젝트에 참여하려면 관리자에게 초대 링크를 요청하세요.`, the visible `초대 링크` input and `초대 열기` action. Also provide `프로젝트 새로고침` and `다른 계정으로 로그인`. One region failing must not disable the other.
- Creation region: use heading `새 프로젝트 만들기`, visible `그룹` selection and `프로젝트 이름` input, help text `프로젝트를 만들면 이 프로젝트의 관리자가 됩니다.`, and real `프로젝트 만들기` submission. Select only from returned own groups; show the selected group's reason when creation is unavailable. A sole eligible group may be preselected. Multiple groups remain explicitly selectable; retain creation-options pagination and label an empty later page as an empty page, not absence of all groups. Name uses required/maxLength 200 and matching server validation; preserve it across request failures.
- Permission/no-group region: MEMBER sees `이 그룹에서는 소유자 또는 관리자만 프로젝트를 만들 수 있습니다.`; legacy null sees `이 그룹의 생성 권한이 아직 설정되지 않았습니다. 그룹 관리자에게 권한 확인을 요청하세요.`; no groups sees `프로젝트를 만들 그룹이 아직 없습니다. 운영 관리자에게 그룹과 소유자 설정을 요청하거나 프로젝트 초대 링크로 참여하세요.` Never promote the first login or fill legacy roles automatically. Do not invent an unimplemented setup link. Provide `요청 내용 복사` with visible, selectable request text containing the authenticated account ID and selected group name/ID when available; it asks the user's administrator to check/set the documented group role or create the project. This copies locally and never sends a message or invents an administrator contact. Clipboard failure leaves the text selectable and explains manual copying.
- Creation lifecycle: while submitting, announce `프로젝트를 만드는 중입니다.` and prevent duplicate submission. Success invalidates project list/lookup data and opens the actual newly created project's dashboard. 400 attaches field errors; 403 keeps safe input, explains that creation permission changed, disables further submit until options refresh, and offers `생성 권한 다시 확인` plus the request text. Network/5xx errors explain failure and retain input; never automatically retry a create mutation. If the result is uncertain, offer project-list refresh before another explicit submit rather than claiming no project was saved.
- Invitation entry accepts the existing same-origin absolute invitation URL or `#/invitations/{token}` / `/invitations/{token}` paths. Parse the URL; permit only the actual invitation route and current origin, with no query, extra path, or external redirect. Trim surrounding whitespace. Invalid input stays on the page with an associated error; submitting never navigates to arbitrary input or invokes acceptance automatically.
- Invitation detail continues to fetch and validate on the server before showing actions. Accepted invitations show `프로젝트에 참여했습니다.` and `프로젝트 열기` pointing to the response's project ID, plus `프로젝트 선택`. Rejected/expired/conflicting invitations explain that a new invitation is needed and offer project selection; preserve current accept/reject semantics and duplicate-submit guards. Describe Calendar as a later reflection that does not block project entry.
- Wrong-account invitation 403 explains that the invitation cannot be used with the current account, offers `다른 계정으로 로그인`, and preserves only the validated invitation route for login continuation. A 404 says the invitation could not be found; an expired invitation requests a new link. Do not invent an invitation inbox/list API.
- Account recovery uses the existing logout endpoint with CSRF. While pending, disable that action and announce progress; on success clear user-scoped query data and show the existing Google login flow. Retain the safe invitation continuation for account switching. A failed logout keeps the current screen, provides an error/retry, and never claims the account changed. The action ends the AI ERP session; Google may require account selection in its own login UI.
- Successful project list: preserve membership order and links, existing page size, and existing role display. Only show pagination when relevant. Empty later pages say `이 페이지에 프로젝트가 없습니다.` with `이전 프로젝트` or first-page recovery, never the global no-membership claim. Returning from an invitation or refreshing invalidates project-list and selected-project lookup data.
- Stale selected project: after a successful completed lookup with no match, show a dedicated heading and `선택한 프로젝트가 삭제되었거나 현재 계정에 접근 권한이 없습니다.` Offer `프로젝트 선택` and `접근 상태 다시 확인`; keep the URL until the user chooses another route. Do not silently select a different project or show project-specific controls without an accessible project.

## State and accessibility coverage

| State | Visible outcome and enabled next path |
| --- | --- |
| Initial/auth loading | Keep the current auth shell; announce what is loading. Do not flash empty projects or business controls before authentication succeeds. |
| Project loading | Show `프로젝트를 불러오는 중입니다.`; keep account/global navigation usable. Do not render empty state until the first page succeeds. |
| Initial list error/network/5xx | Explain `프로젝트를 불러오지 못했습니다.` with `다시 시도`; creation capability, invitation entry, and global navigation remain independently usable. Do not label this no membership. |
| Background refresh/partial | Preserve already loaded, non-sensitive content with visible refresh progress; disable only the duplicate refresh action. If refresh fails, explain that visible data may be out of date and keep retry. Never hide access-denial feedback behind cached success. |
| Empty first page | Membership explanation and creation question, server-driven creation form or precise unavailability reason/request copy, invitation entry, refresh, and account switching; no useless disabled pagination pair. |
| Creation capability loading/error | `프로젝트 생성 권한을 확인하고 있습니다.` until completion; on failure explain inability to check with `생성 권한 다시 확인`. Do not equate unavailable capability data with denied permission; invitation entry remains usable. |
| Creation allowed/denied/unconfigured | OWNER/ADMIN may submit in their own selected group. MEMBER, null role, and no-group cases have distinct explanations/request text. A role changed after loading is enforced again by POST and recoverable by refresh. |
| Missing/stale selection | Dedicated unavailable-project explanation with project selection and lookup retry. No dashboard/form API is enabled solely by a stale route. |
| 403 | Explain insufficient access and offer project selection. For invitation 403 use account-mismatch recovery. For an action-level 403 do not claim project deletion; preserve safe form input and offer access refresh. A server denial overrides cached UI capability. |
| 404 | Explain that the requested item is unavailable with a relevant parent/project-selection link. A missing schedule is not proof that its project disappeared. |
| 401/session expired | Explain that login is required and use the existing auth flow; remove stale protected content and user-scoped cache. Safe invitation continuation survives; never retry mutations automatically after login. |
| Success/disabled | Created project opens its real dashboard; accepted invitation offers the actual project route. Pending create/accept/reject/logout/retry actions announce progress and reject duplicate submissions. Permission-disabled actions explain the needed role; no fake navigation. |

- Use real `<a>` links for routes and `<button>` for refetch/logout/submission/copy. Each recovery surface has a heading; invitation and project-name inputs and group selection have visible labels, help text, and `aria-describedby` errors with `aria-invalid` on failure. Enter submits only the focused form; Tab order follows visual order. Creation validation focuses the first invalid field. Copy success/failure is announced without moving focus.
- Keep focus on a retry control after a recoverable request where it remains mounted. On deliberate route changes move focus to the new primary heading without trapping focus; when a success action removes the focused control, move focus to the success heading/next action. Do not autofocus inputs on initial mobile load.
- Announce loading/success via `role="status"` and errors via `role="alert"`, without duplicating announcements. Existing visible focus treatment and high-contrast palette remain. Error state is conveyed by text, not color alone. Long links/user identifiers wrap; do not display invitation tokens in debug output.
- At 1280px and 390px viewports, use the existing fluid section and wrapping controls. Recovery content/input fits the viewport; header navigation wraps and controls remain at least comfortably touchable (target 44px height). No horizontal scroll or decorative motion. Table/filter/sort/bulk interaction is not applicable to this recovery form; existing project pagination is retained as specified.

## Decisions and acceptance criteria

- Decision: implement documented group creation authority and actual project creation alongside the existing invitation/logout paths. Legacy missing roles remain explicitly unconfigured, preserving the distinction between incomplete setup and a known permission denial; independent ProjectRole enforcement remains unchanged.
- Decision: distinguish empty, unknown, unavailable, permission, and request failure. Retry refreshes actual server state; a 403 cannot be resolved by repeatedly enabling forbidden actions, and 404 does not imply global project loss.
- AC1: signed-in `GET /projects` returning `[]` on page 0 shows explanation, creation question and capability-driven next action, functional invitation entry/refresh/account actions, and no dead pagination. Delayed/error responses never flash the empty state or falsely deny creation.
- AC2: valid invitation entry opens detail, explicit acceptance calls the existing API once, and success reaches the accepted project. Invalid/external URLs never navigate or call an invitation API; input remains editable with accessible feedback.
- AC3: absent or revoked project lookup shows the unavailable state across dashboard, schedule list/detail/form, members, and invitation creation. Retry can recover a restored membership; project selection reaches the list without an automatic redirect loop.
- AC4: list/detail 500 or network failure can recover by retry; repeated retry while pending starts no duplicate operation. 403, 404, and 401 show distinct user language and relevant next actions. Session expiry does not leave old protected data visible.
- AC5: cached project capability followed by a server 403 cannot leave protected data/actions treated as current; action-level permission loss preserves entered data where safe. Independent Calendar failures remain local and do not block project navigation.
- AC6: pagination after the first page, projects beyond page 0, valid login invitation continuation, existing viewer/member/manager gating, and 409 form recovery continue to work. Account switching clears private cached data and restores only a safe invitation path.
- AC7: OWNER and ADMIN with zero projects can create in their own group, receive explicit MANAGER membership only for the new project, and reach its dashboard. MEMBER, legacy null role, no membership, and another user's group are rejected by the server with no partial records. Creation-options pagination reaches an eligible group beyond the first page. The legacy migration preserves null role and existing membership/ProjectRole values.
- AC8: creation-options errors/loading do not masquerade as denied authority; selected-group reasons distinguish MEMBER/null/no groups. Copy-request action reports actual success or accessible manual fallback. Invalid name/group errors preserve input; duplicate clicks submit once; role loss between options and POST returns actionable 403; creation success refreshes navigation and project lookup. No role assignment or first-group provisioning occurs from ordinary login.
- Planned checks: focused Vitest/Testing Library regressions for these branches and request counts; run the existing frontend suite, typecheck, and build. Add backend authorization/creation tests, transaction/persistence coverage, legacy migration verification, and REST Docs/OpenAPI generation for new endpoints. Use actual browser reproduction and post-fix scenarios at desktop/mobile sizes with network/console inspection, keyboard-only recovery, focus, and error/loading/empty screenshots. A test server or intercepted API scenario must be labeled as such and never described as real OAuth/account validation.
- Checks not run by designer: runtime/browser reproduction, frontend/backend tests, real OAuth, production verification, and implementation accessibility. The implementation task owns those results. This plan does not certify implementation.
- Open decisions: no verified first-group/first-owner bootstrap policy exists in inspected sources. This fix implements creation for explicit OWNER/ADMIN rows and explains unresolved setup without inventing bootstrap or promotion. An operator must use the existing approved provisioning process when one exists; this plan does not claim such a process was found. Independent reviewer must re-evaluate the changed scope, creation contract, permissions, state coverage, and AC7–AC8 in `docs/ux/2026-09-07-post-login-recovery-review.md`; the earlier pass for invitation-only scope is superseded.
