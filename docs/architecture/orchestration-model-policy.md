# AI ERP 모델 오케스트레이션 설계

작성일: 2026-09-07. 상태: 모델 정책 구현·독립 검토 완료. 이 로컬 파일이 원본이며 Notion `AI 생성문서 관리`에 보관한다.

목적은 필요한 판단 품질을 유지하면서 작업당 토큰 사용과 중복 실행을 줄이는 것이다. Astra는 최상위 감독과 최종 독립 검토를 맡고, 일반 기획·분류·설계는 Sol, 확정된 실행은 Luna가 맡는다. Spark는 부모가 이유를 기록하고 선택하는 구현 대안으로 둔다.

| 역할 | 기본 모델 / 추론 | 책임 |
| --- | --- | --- |
| 상위 오케스트레이터 | Astra / high | 범위·설계·권한 결정, 하달, 결과 수락 |
| router | Sol / medium | 필요한 경우 요청 분류와 지시서 정리 |
| product-planner | Sol / medium | 점진적 제품 기획과 계층별 요구사항 |
| ui-ux-designer | Sol / medium | 화면·사용 흐름·상태·접근성 설계 |
| reviewer | Astra / high saved default; normal plan review Sol / medium when explicitly selected | 위험 등급에 따른 독립 검토와 판정 |
| implementer | Luna / high | 확정된 계약의 코드·테스트·설정 구현; Spark / high 명시 선택 가능 |
| release-manager | Luna / high | 배포 계약 준비와 승인된 기존 운영 명령 실행; 판단·검토는 Astra |

모델 식별자는 `gpt-6-astra`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.3-codex-spark`를 사용한다. 저장된 reviewer 기본값은 Astra/high이며, 정상적인 `increment-plan-review`·`ui-plan-review`는 부모가 명시적으로 선택한 read-only Sol/medium을 사용할 수 있고 고위험 계획·릴리스 검토는 Astra/high를 사용한다. 고위험·복합 실행 호출에는 모델과 추론 수준, 문맥·결과 예산을 기록하고 저위험·표준 실행은 `TASK-RECORD.md`에 간결하게 기록한다.

업무 흐름은 상위 판단 → 필요한 Sol 전문 기획 → 완성된 지시서 → Luna 구현 → `harness/policies/VERIFICATION.json`의 위험별 검사·검토 → 상위 수락이다. 저위험 작업은 해당 빠른 검사와 부모 수락으로 완료할 수 있고, 표준 작업은 변경 영역 검사를 기본으로 하며 Sol/medium 검토를 필요할 때만 선택한다. 고위험 작업은 관련 통합 검사와 Astra/high 독립 검토가 모두 필요하다. 상위가 이미 분류한 단순 작업에 분류 에이전트를 추가 호출하지 않는다. 화면 설계와 독립 `ui-plan-review`의 필수 선행조건, 제품 계획·릴리스 검토 게이트는 유지한다. 프런트엔드와 백엔드 구현은 각각 범위·의존성이 명시된 계약으로 같은 구현 역할에 하달한다.

토큰 절감은 다음 절차로 관리한다.

- 기본 실행자는 한 명이며, 서로 독립적인 작업만 최대 두 명까지 병행한다. 위임 깊이는 1로 제한한다.
- 새 에이전트에는 전체 대화 대신 현재 계약·관련 역할·필요한 소스 경로를 전달한다. 전체 이력 전달에는 별도 이유를 기록한다.
- 고위험·복합 지시서에는 입력 문맥 예산, 읽을 소스 목록, 결과 예산을 명시한다. 저위험·표준 작업은 `TASK-RECORD.md`의 최소 필드로 충분하며, 필수 요구사항을 잘라내는 대신 작업을 나눈다.
- 같은 문맥의 수정은 결함과 변경분만 전달한다. 완료된 검증은 변경이나 남은 의문이 있을 때 다시 실행한다. 행동 변경 배치가 끝날 때 관련 전체 모음을 한 번 실행하고, UX·provider·Git 검사는 해당 변경이 있을 때만 실행한다.
- 결과 요약은 기본 250단어 이내와 근거 링크를 목표로 한다. 원시 로그는 파일에 보관한다.
- 실제 제공된 토큰·캐시 사용량과 실행 시간만 기록한다. 제공되지 않은 작업별 사용량을 0으로 표시하거나 계정 전체 사용률로 대체하지 않는다.

모델 승격은 Astra 판단자가 결정한다. 지시가 명확한데도 요청을 이해하지 못하거나 계약대로 수행하지 못했다는 근거가 있으면 `Luna/high → Terra/medium → Sol/medium` 순서에서 다음으로 충분한 모델을 선택한다. Spark/high는 Luna 단계의 명시적 구현 대안이다. 역할의 저렴한 기본값은 유지하고 해당 작업의 호출만 바꾼다. 처음 실행을 포함해 영향받은 작업의 시도는 최대 세 번으로 제한한다.

승격 기록에는 기대·실제 결과, 실패 분류, 이전 시도, 선택 이유, 새 지시 버전, 검증 기준과 남은 횟수를 적는다. 지시 자체가 모호하면 지시를 고치고, 일반 코드 결함은 충분하다면 같은 모델로 제한된 수정을 한다. 모델을 올리면 반드시 해결된다고 가정하지 않는다.

Sol에서도 실패하면 하위 실행자를 Astra로 올리지 않는다. 최상위 Astra가 자신의 하달 내용, 작업 분해, 제공 문맥, 인터페이스·선행조건과 수용 기준을 재검토한다. 이후에는 실제로 수정된 범위·근거가 있는 지시를 내리거나 필요한 정보와 해결 방향을 제시한다. 작업 ID나 버전만 바꿔 재시도 횟수를 초기화하지 않으며, 자기 재검토를 독립 검토 통과로 취급하지 않는다. 이미 Sol을 쓰는 하위 기획·설계 역할도 같은 상한을 적용한다.

외부 설정 누락과 사용량 제한은 이해 능력의 실패로 취급하지 않는다. 이를 우회하려고 비싼 모델로 승격하거나 모델을 차례로 시험하지 않는다. 승인된 동급 구현 대안의 가용성이 확인됐다면 부모가 명시적으로 하달할 수 있고, 그렇지 않으면 제한 근거·해결 방향·재개 조건을 반환한다. Astra 최종 검토가 불가능하다고 검토를 생략하거나 구현자가 승인하지 않는다. 계정 크레딧 구매나 초기화는 별도 명시적 요청 없이 실행하지 않는다.

외부 API 설정 차단도 같은 원칙을 따른다. 계정·권한·콜백 등 필수 조건이 없거나 확인되지 않았으면 의존 작업을 멈춘다. 목표 모드는 이 중단 조건을 우회하지 않는다. 이미 승인된 독립 오프라인 작업만 해당 범위로 진행하며 실제 연동 성공으로 취급하지 않는다.

이 설계의 설정·하달·문맥 규칙은 구조 검사로 확인한다. 실제 토큰 절감률은 비교 가능한 작업별 사용량이 확보된 뒤 평가해야 하며, 현재 수치로 입증됐다고 주장하지 않는다.
