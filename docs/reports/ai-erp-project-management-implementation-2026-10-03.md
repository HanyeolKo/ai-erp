## 백엔드 B1

B1은 제품 코드를 바꾸지 않고 지정된 검사 파일 세 개를 보강했다. 검색 결과가 두 항목임을 정확히 확인하고, 마이그레이션 시각을 UTC instant로 비교하며, 의도한 receipt `CHECK` 실패의 SQLSTATE와 제약 이름을 확인하도록 PostgreSQL 검사를 강화했다. 잘못된 값이나 누락된 조건을 거절하면서 원본 바이트를 보존하는 정규화 검사도 추가했다. 독립 검수에서는 PostgreSQL 회귀 검사와 정규화 검사 범위를 소스 수준에서 닫았다.

OpenAPI 계약 검사는 요청 예제를 별도로 읽도록 바뀌었지만, 기존 응답 예제의 `health`, `healthReason`, `healthAsOf` 단언을 대체해 버렸다. 요청과 응답을 모두 검증해야 하므로 `B1-OPENAPI-CONTRACT`의 P2 결함은 열려 있다. 이 때문에 B1의 독립 검수 결과는 계속 `FAIL`이다.

JDK 25 환경에서 백엔드 최종 테스트, 통합 검사 컴파일, OpenAPI 생성과 `bootJar`가 종료 코드 0으로 끝났다. 로컬 Docker가 없어 실제 PostgreSQL 검사는 실행하지 않았지만, 같은 SHA의 최종 CI에서 통합 검사 61개가 모두 통과했다. 이 성공은 누락된 요청·응답 동시 단언을 대신하지 않는다.

## 프런트엔드 F1

F1은 빠른 작업 생성 결과를 조정할 때 요청 종류와 데이터 구조를 먼저 확인하도록 제품 코드를 보강했다. 실제 Chrome에서 기존 TASK 상태 변경이 `PATCH 200`으로 끝난 뒤 빠른 작업 생성이 올바른 제목과 상태로 `POST 200`에 성공했다. 화면은 빈 상태가 되지 않았고 `body.requestId` 예외도 재현되지 않았다. 키보드로 두 번째 작업을 생성했을 때에는 새로운 UUID가 사용되었다. 독립 검수는 `F1-QUICK-CREATE-CONTINUITY` P1을 소스와 실제 영향 범위 관찰에서 닫았다.

로컬 전체 검사는 30개 파일의 358개 검사가 모두 통과했고, 타입 검사와 빌드도 종료 코드 0으로 끝났다. 같은 결과는 최종 CI에서도 통과했다. 실제 Chrome에서는 390×844과 640×450 화면에 문서 가로 넘침이 없었고, 결과를 알 수 없는 요청의 동일 UUID·본문 재확인, 409 뒤 수정·새 UUID, 지연된 생성 중 화면 왕복, 역할별 작성 가능 여부와 영역별 오류 표시가 지정된 오프라인 픽스처에서 유지되었다. 소유한 브라우저 서버 14개는 검증 뒤 2026-10-04 03:17:39 KST에 모두 중지되었고 원본은 보존되었다. 이 자료는 실제 ERP·Google 연동이나 실제 배포를 입증하지 않는다.

`F1-REPAIR-REGRESSION-COVERAGE` P2는 계속 열려 있다. 화면을 떠나기 전에 가짜 타이머를 설치해야 하는데 부모가 작성한 6차 준비 문서가 순서를 반대로 지시했으며, 이는 작업자나 모델의 불이행이 아니다. 실제 보호 캐시가 먼저 존재한 뒤 403으로 제거되는지 확인하는 검사, 이전 세션의 요청이 끝날 때까지 기다린 뒤 새 사용자와 초안이 영향을 받지 않는지 확인하는 검사도 충분하지 않다. 잘못된 빠른 생성 요청 기록, 연속 ASCII 입력, `beforeunload`, 서로 다른 빈 상태, 차단 정보, 기본 모드 경로, 로딩·재조회·오류·재시도 등 기존에 이름이 지정된 영향 범위 검사도 남아 있다.

독립 Astra/high 추가 검수는 실제 Chrome 원본을 확인한 뒤에도 전체 결과를 `FAIL / changes-requested`로 유지했다. P1은 닫혔지만 P2 검사 공백이 남았으며, 이 공백은 새로운 제품 장애가 확인되었다는 뜻은 아니다.

## 사용할 수 있는 범위와 남은 범위

현재 초안에는 프로젝트 관리의 백엔드 운영 정의, TASK 실행 정보, 개인 작업 API와 프런트엔드 TASK 진입점, 기본 작업 화면, 개요 요약, 역할별 읽기 전용 표현이 포함되어 있다. 그러나 B1과 F1이 모두 수락되지 않았으므로 완성본이나 배포 가능한 결과로 취급할 수 없다. 실제 ERP·Google 연동과 배포 성공도 확인되지 않았다.

S2의 운영 정의 설정 화면, TASK 실행 정보 편집·확인 화면, 내 작업 화면, 일정 문맥과 파일 연결 기능은 구현되지 않았고 배정되지 않았다. S3의 마일스톤 검토와 주간 위험 기능도 구현되지 않았고 배정되지 않았다.

사용자가 이전에 최종 병합을 승인한 사실은 유지된다. 그러나 필수 검수가 실패했으므로 PR #26은 초안 상태를 유지해야 하며, 병합이나 배포를 실행할 수 없다.

## 다음 작업

6차 수정은 사용자의 승인을 받아 실행되었지만 독립 검수를 통과하지 못했다. 수정된 [7차 검증 준비 문서](<C:/Users/USER/.codex/worktrees/project-management-redesign/AI ERP/docs/planning/pm-implementation-2026-10-03/exception7-verification-preparation.md>)는 정확한 파일 네 개만 다루는 제안이다. 범위는 백엔드 `OpenApiContractTest.java`, 프런트엔드 `pm-default-workspace.test.tsx`, `session-boundary.test.tsx`, 그리고 `Schedules.tsx`에서 접근 거부 시 프로젝트 계획 캐시를 제거하는 한 줄이다.

정적 확인에서는 `Schedules.tsx`가 실제로 채워진 `TASK` 종류의 캐시 키 대신 빈 종류의 캐시 키를 제거하는 불일치가 발견되었다. 7차가 승인되면 현재 캐시에 성공 데이터가 있는 403 시나리오를 먼저 실패하는 검사로 재현해야 하며, 캐시 부재는 쿼리 객체 개수가 아니라 조회 데이터가 `undefined`인지로 확인해야 한다. 이는 아직 실행된 7차 실패나 새로운 소스 판정이 아니다.

B1과 F1에는 각각 같은 Luna/high 구현자의 한 차례 추가 수정이 제안되어 있다. 일반 상한 3회와 예외 4·5·6차는 이미 사용했으며, 횟수 초기화나 등급 변경은 없다. 7차는 현재 `UNAUTHORIZED / UNASSIGNED`이고 사용자의 새 승인을 기다린다. 제품 소스는 수정되지 않았으며 S2·S3 진행 권한도 부여되지 않았다.
