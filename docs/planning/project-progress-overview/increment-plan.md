## Problem, users, value, and priority

- Project MANAGER, MEMBER, and VIEWER users need an honest macro progress reading first, followed by their active assigned work and today's/this-week project schedules, without reconstructing status across Plan and Schedules.
- Product information priority is: whole-project TASK completion and plan target/forecast; plan goals and critical risks; milestones; signed-in user's active TASKs; then today's/this-week project schedules and existing confirmation work. UI structure, layout, interaction order, and presentation remain deferred to `ui-ux-designer`.
- “Project progress” means unweighted non-cancelled TASK completion only: `doneCount / taskCount` and the API `progressPercent`. It is never a weighted business-health, value-delivery, EPIC, or schedule percentage. With `taskCount=0`, report no percentage.
- Preserve existing notifications, schedule confirmation semantics, plan model, project membership, editor destinations, and separate task/schedule ownership. Reading Overview performs no mutation, including schedule acknowledgement or automatic notification mark-read; existing read-only notification retrieval remains permitted, and explicit user-triggered notification behavior stays under its existing owner.

## Current slice, selection rules, and deferred scope

- Fetch one unfiltered `GET /api/v1/projects/{projectId}/plan` snapshot. Use its whole-project `summary`, `targetStart/targetEnd`, `asOfDate`, items, and item summaries; never recompute the headline denominator from filtered or displayed rows. Server `asOfDate` (UTC aggregate date) is authoritative for overdue checks.
- Report manual project target separately from computed forecast. Map `EMPTY`, `UNDATED`, `INCOMPLETE`, and `COMPLETE` literally; an incomplete forecast may show known bounds only with an incomplete label. `outsideTarget` is a comparison flag, not a health score or delivery prediction.
- “Plan goals” are non-cancelled EPICs, with their existing descendant-TASK summaries. TOPIC summaries supply goal detail without creating weights. Prioritize goals with blocked/overdue descendants, then outside-target/incomplete forecast, then existing `sortOrder` and id. Limit overview preview to 3; the destination remains the existing Plan views.
- “Critical risks” are existing active TASKs that are blocked (`state=BLOCKED` or `blockerIds` non-empty), overdue (deadline, else targetEnd, before `asOfDate`), unplanned, or unassigned. Report the authoritative summary counts and preview at most 5 tasks ordered blocked, overdue, unplanned, unassigned, nearest applicable date, `sortOrder`, id. Do not invent severity or automatic project-health labels.
- “Milestones” are non-cancelled MILESTONE items, previewed up to 5 by deadline, targetEnd, targetStart, `sortOrder`, id, with undated last. Their state/date is descriptive; they do not enter TASK completion.
- “My work” is at most 5 non-DONE/non-CANCELLED TASKs whose `assigneeId` equals `/api/v1/me.id`, ordered blocked, overdue, `IN_PROGRESS`, nearest deadline/targetEnd, `sortOrder`, id. Its count stays separate from project totals. The supported destination is `/projects/{id}/plan?view=tasks&types=TASK&assigneeId={me}` and must be named “all assigned tasks” because the current endpoint includes DONE by default; no active/multi-state/blocked-only query is invented.
- “Today / this week” remains project schedules, not “my schedules”: creator, participant, and acknowledgement target are distinct. Tasks and schedules have separate counts, empty/error states, and destinations; no automatic relation or combined metric is implied.
- Defer cross-project work, a personal-schedule ownership rule, task-schedule relations, weights/business health, new operating definitions/widgets, detailed Plan density/context work, backend/schema/API/permission changes, provider activation, and shared-widget extraction.

## API, date, completeness, permission, and ownership requirements

- Reuse only `/api/v1/me`, project membership, `/plan`, `/schedules`, and the existing dashboard/notification reads. No new endpoint, query contract, database object, V11 migration, or permission is allowed.
- Schedule zone is a valid IANA zone from overview URL context, defaulting to existing `Asia/Seoul`. “Today” is that zone's civil date. “This week” is Monday 00:00 through next Monday 00:00. Convert boundaries with existing civil-date helpers and query half-open instants `[from,to)`; include schedules when `endsAt > from && startsAt < to`. Fetch the week once and derive today from the same rows and overlap rule.
- Traverse `/schedules` with `limit=20`, pages 0 through 49 only: at most 50 requests. Deduplicate by schedule id before counts or period derivation. A page with fewer than 20 rows ends `complete`; a full page that adds zero new ids stops immediately as no-progress `partial`; 50 full pages stop as ceiling `partial`; any non-access later-page error is `partial`. Partial labels/counts say “loaded” rather than imply totals. A successful empty first page is `empty`; a non-access first-page failure is `unavailable`.
- Plan `complete=true` permits total counts and percentages; `complete=true,totalCount=0` is `empty`. `complete=false` is `partial`: returned rows may remain explicitly partial, but project totals/percentages cannot be presented as complete. A non-access first-read failure is `unavailable`.
- Project membership is the shared protection boundary. `PROJECT_ACCESS_DENIED`, or a 403/404 from project lookup, immediately enters one project-wide `access-failure`: hide and discard cached Overview dashboard, Plan, schedules, confirmation queue, and configured project-card data; cancel/remove their project-scoped queries; lock project actions. A 403/404 from a protected project resource is treated the same when it denotes project access denial. Global 401 keeps the existing session-termination handling rather than this project-only recovery.
- Every protected response is accepted only for the active session generation, project id, project-access revision, and, for schedule results, current zone/from/to selection. Denial, logout/session replacement, project switch, or date/zone switch invalidates the prior request epoch; a pre-denial or obsolete late success cannot repopulate data or clear the lock.
- Recovery starts a new access revision. No cached result restores visibility: a region returns only after a fresh successful membership lookup and a fresh successful read of that region's relevant resource in the same active session/project/date-zone context. Failure of either read keeps that region and all still-unverified project regions blocked; repeated failure never clears the project-wide lock. No PR26 cache/recovery behavior is adopted.
- Existing roles remain authoritative: members may read plan and schedule data; existing capability checks alone govern create/edit/confirm/acknowledge actions; VIEWER stays read-only and receives no action queue. Overview links to current owners and never broadens access.
