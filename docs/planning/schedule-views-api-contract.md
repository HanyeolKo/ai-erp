# Schedule workspace API contract

- Task `schedule-views-delivery`; contract r2, parent `/root`; implementation is blocked until selected increment and functional/visual UI review pass. Base `49d79fe553bb4048a72671b503609e2d2c38ce58`. r2 resolves API-PROPERTY-ORDER-001 and freezes transaction/initial-version semantics.
- Prefix `W=/api/v1/projects/{projectId}/schedule-workspace`. Existing schedule APIs, DTOs, lifecycle and projection behavior stay compatible. New interfaces are additive.

## Wire model

- `Scalar = string | number | boolean | null`; values map keys are project property UUIDs; null clears a value. Missing keys on PATCH preserve stored values.
- `Property = {id,name,type,position,archived,rowVersion,options}`; `type=TEXT|NUMBER|CHECKBOX|DATE|SINGLE_SELECT`, immutable after create. `Option={id,label,color,archived}`; option IDs stable UUIDs. Dates use strict ISO local `YYYY-MM-DD`, numbers finite, text max2000. Property name1..80; option label1..80; text is rendered as text, never HTML.
- `PropertyWrite={name,type?,position?,archived?,rowVersion?,options?:[{id?,label,color,archived?}]}`. position integer0..10000, create default next position, omitted PATCH preserves; sort properties by position then id. Supplied option-array order is canonical and persisted; PATCH requires all current options if options supplied, rejects accidental omission; IDs assigned for new items and archive preserves data. No hard delete/type conversion. Type mismatch400; stale version409. All PATCH requests require rowVersion.
- Color tokens only `gray|blue|green|amber|red|purple|pink|teal`. Names and color both presented; fixed status badges remain independent.
- `Field` is fixed `title|startsAt|endsAt|status|createdBy` or `property:<uuid>`.
- `Filter={field,operator,value?}`; AND only; `EQ|NE|CONTAINS|GT|GTE|LT|LTE|IS_EMPTY|IS_NOT_EMPTY`. Text: EQ/NE/CONTAINS/empty; number/date/time: EQ/NE/comparison/empty; checkbox/select/status/creator: EQ/NE/empty. No implicit coercion. Unset satisfies only IS_EMPTY and NE when comparing nonnull; explicit empty operators have no operand.
- `ViewConfig={type,filters,sorts,groupBy,legendBy,visibleFields}`; type `CALENDAR|CARDS|LIST`; sorts array `{field,direction:ASC|DESC}`; groupBy/legendBy null or SINGLE_SELECT property UUID (without property prefix); visibleFields Field[]. Title always shown. Group/legend independent. Calendar always maps fixed start/end. Null sort values last, UUID final tie-break; SINGLE_SELECT sort follows option order then UUID.
- `View={id,name,scope,ownerId,rowVersion,archived,config}`; scope `BUILTIN|PERSONAL|SHARED`; builtins `builtin-calendar|builtin-cards|builtin-list`, revision0, immutable and available to every authorized reader without persisted initialization.
- `ViewWrite={name,scope,config,rowVersion?,archived?}`; name1..80, scope only PERSONAL/SHARED, immutable after creation. Personal→shared means explicit new copy, not ownership mutation.
- `Workspace={properties,views,dashboardViewId,dashboardRowVersion}`. Absent dashboard row is null reference/version0; first successful PATCH requires expected0 and returns stored version1, subsequent edits increment. All definitions including archived are readable for historical values. Views include builtins, active shared and actor-owned personal views; no other user's personal definitions.
- `Record={schedule:<existing ScheduleResponse>,values:<map>}`. Existing ScheduleResponse stays unchanged; record identity is schedule.id.
- `Query={config,from?,to?,page?,size?}`; date window half-open overlap `endsAt>from AND startsAt<to`; defaults page0/size50, max100; page>=0 bounded100000. Date window optional for list/cards; calendar supplies full visible range.
- `QueryResult={records,total,hasMore,page,size,groups,queriedAt}`; groups `{optionId:string|null,label,color:string|null,count}`. Counts computed for full filtered scope before pagination, including unset and archived option labels. No groupBy gives groups[]. queriedAt is informational, not a snapshot token.

## Endpoints

- GET `W` → Workspace. Read only, no seed writes.
- POST `W/properties` PropertyWrite → Property; PATCH `W/properties/{id}` PropertyWrite → Property. MANAGER only. Server project lock and fresh role check; cap50 definitions and100 options each (including archived, fail explicit400 at cap).
- POST `W/views` ViewWrite → View; PATCH `W/views/{id}` ViewWrite → View. MANAGER shared; MANAGER/MEMBER own personal. VIEWER reads only. Server validates each config ID/type/operator on write and query. Max100 shared and100 personal views per project/actor, including archived. Builtin edits rejected; duplicate creates a new view.
- PATCH `W/dashboard` `{viewId,rowVersion}` → `{dashboardViewId,dashboardRowVersion}`; MANAGER only. null resets builtin-cards. Only active SHARED or builtin view accepted. No personal embedding or privilege promotion. On later archive/unavailability, return reference and unavailable UI state with explicit reset rather than stale content.
- POST `W/query` Query → QueryResult. All project readers. HTTP POST still uses normal existing CSRF/session helper; no mutation or external call. Strict typed server query, authorized project before SQL; predicates/counts/sorts in database, then paging; never fetch one page and filter in memory.
- GET `W/records/{scheduleId}` → Record (authorized existing detail plus values).
- POST `W/records` `{schedule:<existing Write>,values?:map}` → Record. Existing writer creation rights; validate values before commit; schedule/participants/value write atomic; one underlying schedule ID.
- PATCH `W/records/{scheduleId}` `{schedule:<existing Write including rowVersion>,values?:map}` → Record. Same manager/creator rules and cancelled-edit rules as existing API. Validate original expected version once under lock, then atomically apply fixed/value updates and return final flushed rowVersion; never pass original stale version to a second value mutation after core update. Value-only changes do not invoke business change semantics.
- PATCH `W/records/{scheduleId}/values` `{rowVersion,values}` → Record. Existing schedule edit permission/cancelled rules; touch same schedule rowVersion, preserve businessRevision/ACK/projection. Empty/no-op patch leaves revision stable. Conflict forces explicit reload/retry; never blindly replay.

## Validation, concurrency and storage invariants

- Caps:10 filters,3 sorts,30 unique visibleFields; property-backed fields must belong to project. Allow archived references in existing configurations and read queries; prohibit new value assignments to archived property/option, but permit unchanged stored archived values and explicit clear. UI labels archived references and offers remove filter/unarchive, never silently changes predicate.
- No invented default property definitions/categories: user creates them. Builtin configs have empty filters, sorts startsAt ASC, group/legend null and visibleFields title/startsAt/endsAt/status. Builtin Calendar exposes month/week; Cards/List remain peers.
- Definitions/options and typed value rows normalized; view config versioned JSON stored with server validation. Values uniquely identify project/schedule/property and type; foreign keys bind option→property and property/schedule→project. Existing data preserved by additive V9 migration. No personal context database or widget engine.
- Configuration writes and value validation serialize against stable project row; consistent lock order project→schedule; fresh authority after lock. For old schedule writes, existing optimistic rowVersion detects custom-value changes. Check foreign IDs before returning metadata; no cross-project counts or personal-view leakage.
- A single query response obtains count/groups/page from PostgreSQL REPEATABLE READ (or equivalent single SQL snapshot); ordinary READ COMMITTED alone is insufficient. Offset pages across separate requests may change with concurrent writes; no frozen snapshot promise. Client deduplicates ID, refreshes after writes, labels partial loading and never labels truncated results complete. Calendar loads all pages for its period up to1000 rows then displays explicit partial state and narrowing guidance; List/Cards keep real pagination and total.
- Separate metadata audit namespace `WORKSPACE_*`, empty notification recipients, appropriate audit aggregate classification; never startsWith SCHEDULE. Custom-only writes generate no Calendar/notification work and no businessRevision change. Real fixed-field edits retain original business events.
- Authorization follows existing project role and schedule creator rules; new config rules do not broaden schedule rights. UI hides forbidden actions, server remains authoritative. Schema archive is reversible and needs affected-value count/clear explanation (can expose counts in Property as optional `valueCount`).
- Required tests: five types/null/empty; rename/archive stability; bad IDs/cross-project/personal access; stale record/config; SQL injection operands; beyond20/100 result/count/filter/group/sort; atomic failure rollback; no metadata projection/notification; old schedule lifecycle/ACK regression; PostgreSQL Flyway and constraints. API docs cover new endpoints; generated client refresh before final frontend checks.
- Frontend uses existing guarded read/mutate helpers and session generation; no raw unauthenticated bypass. Offline UI fixtures are explicitly synthetic and cannot satisfy real DB integration checks.
